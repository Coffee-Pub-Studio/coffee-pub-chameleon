# Weather architecture

**Audience:** a developer changing how Chameleon gets and shows the weather on a day, and an admin deciding what leaves the server. For the route and its answers see [Modules API](../api/api-modules.md), "Weather"; for the page's pieces see [Module SDK](../api/api-module-sdk.md), "The weather on a day"; for what an admin does see [Modules](../userguides/userguide-modules.md), "Weather".

## What it is

Each day of a trip in the Itinerary can show a small icon with the day's high and low. The weather comes from a **provider adapter**, a small module in `server/weather-providers/` for one service that is free for commercial use. Chameleon never uses a paid service (Thomas, 2026-11-25). The server asks the service, keeps what it was told for a while and answers the page and agents from that. The page never contacts the service.

The weather is split in two on purpose. **The engine stays core**: the lookup, the cache, the adapters, the route and the SDK pieces are shared code that names no module that uses them. **The options live in a bundled Weather module**, because people look for options on a module. That module has no window and no code of its own; it is a service-only module, as the AI Assistant is, and the core names it (`modules.enabled('weather')` in `weatherSetup`, `server/index.js`).

## The parts

- **The Weather module** (`modules/weather`, `hooks.weather: true`). Its manifest holds three settings, all of the environment scope: **Service** (`service`, a `choice` marked `"adapters": "weather"`, `None` by default, whose options the server fills from the registered adapters), **Temperatures** (`units`, `c` or `f`) and **Icon style** (a `note`, since one style exists; a choice is added when a second does). The module's own on and off is the only switch: there is no second setting, a module that has days cannot hide weather on its own, and a space cannot turn it off.
- **When weather is used** (`weatherSetup`, `server/index.js`). It answers a service only when the Weather module is installed and on in the environment, `service` names a registered adapter, and that adapter's terms are accepted. Otherwise it answers null, the route answers `configured: false`, and nothing leaves the server.
- **The terms** (`server/weather-terms.js`, `WeatherTerms`). A service's terms are a binding agreement that a person in authority accepts; software cannot. So the acceptance is kept once for the host in `DATA_DIR/weather-terms.json`, `{ services: { <id>: { terms, by, at } } }`, because a module's settings belong to an environment and cannot be the host's. It counts only for the terms address it was given for, so a moved address needs accepting again. Who may accept: on a single install the signed-in `admin`; on a hosted server the host's administrator, on the host console. The call needs that person's own session and an explicit `{ accept: true }`. An owner can read the status and cannot accept; an agent never can. The routes are in [Modules API](../api/api-modules.md), "The terms of a weather service". The host routes are registered before the host router's catch-all, which is why they answer at all. The file is on the migration's keep list when a single install becomes a hosted one; `weather.json` is not.
- **The page for the terms** (`public/weather-terms.js`, `wireWeatherTerms`). One piece used by both pages: on a single install the **Weather terms** section sits under the modules list on the Modules page of Manage; on a hosted server it is on the host console's **Server** page, and an environment's owner sees the status and a sentence that the host's administrator accepts, with no buttons.
- **The lookup and the cache** (`server/weather.js`). `WeatherCache` keeps `DATA_DIR/weather.json` in two parts. `days` is keyed `"lat,lon|YYYY-MM-DD"`, each record `{ code, high, low, rain, got }`. `asks` is keyed `"lat,lon"` and holds `{ at, until, modified, answer }`: when the service was last asked, the earliest it may be asked again, the `Last-Modified` it gave and the stamp of the days that answer gave. Neither part keeps who asked, which space or what for. A forecast is good for 3 hours and a past day for 24; the file holds at most 20,000 days and nothing older than 40 days, and an `asks` entry is dropped a day after its `until`. `askWeather` asks the adapter's address: it sends only a position rounded to 2 decimals and a run of days, has 6 seconds for the whole ask, cuts the body at 400 KB and follows at most 3 redirects, each to a public address that is then asked at exactly the addresses that were checked (the guard link previews use). `weatherDays` joins the cache and the ask, and one ask per position runs at a time.
- **The declaration** (`cleanWeather` in `server/modules.js`). A module with days says in its manifest only where its days' places are in its own stored data (`stops` and `main`), so the core hard-codes no keys. It names no provider and no units: a manifest that does is refused. The Itinerary declares only that (0.16.26 dropped its `weatherProvider` and `weatherUnits`).
- **The provider adapters** (`server/weather-providers/index.js`). An adapter exports `{ id, name, credit, needsKey: false, request, parse }` and optionally `terms`, `headers`, `pastDays`, `aheadDays`, `minAskMs` and `allowHttp`; the contract is in [Modules API](../api/api-modules.md), "Weather". Only a service free for commercial use may be registered. A test stand-in is loaded only when `WEATHER_TEST_STANDIN` is set, for `tools/check-weather.mjs`.
- **MET Norway** (`server/weather-providers/met-norway.js`, Locationforecast 2.0, the compact form), registered. Its terms were read on 2026-11-25 and are recorded in the adapter's header: free for any use, no key and no account, under CC BY 4.0 and NLOD 2.0. What that asks of the code, and where it is done:
  - *Credit.* The adapter's `credit` ("Based on data from MET Norway, CC BY 4.0 ...; our daily summary, not MET Norway's.") is shown in the day's popover and on the terms page, and says plainly that the summary is Chameleon's own, so nothing looks as if MET Norway or Yr made it.
  - *Identification.* `headers()` sends a `User-Agent` of the product name and version with the repository's address (`userAgent` in `server/product-name.js`), the way their terms name as valid. No contact of a person is sent.
  - *Caching.* A request is never repeated before the answer's `Expires`; the last `Last-Modified` is sent back as `If-Modified-Since`, and a 304 keeps what is kept and makes it fresh; the least time between two asks for one position is `minAskMs`, 3 hours, which meets their rule for places outside the Nordic area; after a 429 or a 403 the position is left alone for 30 minutes; a 203 (the version is going away) is logged.
  - *Positions and traffic.* Two decimals are sent where up to four are allowed; requests are https and redirects are followed within the 3-redirect limit.
  - *What it gives.* Forecasts about ten days ahead (`aheadDays: 10`); no past days (`pastDays: false`), so a past day is never asked for and comes back `unavailable`, and a day beyond the ten likewise. The compact form has no chance of rain, so `rain` is `null`. A day is cut from MET's UTC readings to the place's own day by its longitude, and is kept only when its readings cover enough of it; how the high, low and word are chosen is in the adapter's header.
- **The route** (`GET /api/modules/:id/weather`, `server/index.js`). It checks the module's read permission, finds each day's place, asks only for days the cache does not hold, and counts only asks that reach an outside service against the limit (30 per person, module and minute). A day's place is the first stop whose place resolves for the asker to an object with a position, else the trip's main place, found by sending the destination text to Maps' chosen place search (the answer is remembered in memory and never written), else none. The route has no module named in it: it works for any module that declares `weather`.
- **The SDK** (`host.weather.days`, routed through `'weather.days'` in `public/module-host.js` to the route, and `host.ui.dayWeather`, which draws the button on a day header). A sandboxed frame has an opaque origin and no cookies, which is why the page asks through the host.
- **The Itinerary** (`modules/travel/src/travel-lib-weather.js`). Pure functions inlined into the page: which days to ask for (the plan's days cut to 31 back and 14 ahead, under the route's 60-day limit; a trip far in the past or the future asks nothing), where each day is, and what one day hands the SDK piece. `createWeather` decides when to ask: at most one ask per draw; an answer reused for 5 minutes; a change to the days or places asks again after 0.6 s, so a run of changes asks once; `configured: false` (weather off, or a picture map) draws nothing and is not asked again for 10 minutes; a 502, a 429 or any other error draws nothing and waits 60 seconds; an older answer arriving late cannot replace a newer one.
- **Agents** read the same route through the gate and the MCP tool `read_weather` ([Agents API](../api/api-agents.md)). The tool takes the `module` whose days they are, required, and names none itself, so the core no longer names the Itinerary. An agent sees `{ configured: false }` when weather is off.

## What leaves the server

Only when weather is on as above and no picture map is set. To the weather service: what the chosen adapter's `request` builds from a position rounded to 2 decimals and the days, under the adapter's `User-Agent`. To the place search: the destination text, only when a day has no stop place and the destination is not already saved or remembered. Never who asks, the space, the environment or anything else of the trip.

## Known gaps

- The Weather module's page has no "Weather is working" test button.
- A service that fails other than with a 429 or a 403 (a timeout, an unreachable address) is asked again on the next request, bounded by the limit.
- Every redraw rebuilds the day headers, so the piece's fade-in plays again; reduced motion turns it off.
- `server/geocode.js` still follows redirects with a plain `fetch` and no address check, and sends the repository address in its `User-Agent`.
- A negative temperature prints with a hyphen, not a minus sign.
- Whether weather should be its own route part rather than code in `server/index.js` is open (step 3 of its plan).
- No real service was ever reached: MET Norway's terms must be accepted by a person first, and the container has no route out. The lookup is checked only against a stand-in service.
