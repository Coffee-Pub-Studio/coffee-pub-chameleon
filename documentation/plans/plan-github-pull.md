## Why

The agent route is the only way today, and it does not fit the job. Thomas's agent account has 300 writes a day, cannot set the board's column and cannot delete. One piece of work and its column are two writes, so the 382 issues are about 760 writes (three days at the full limit, with nothing else done), and after that every new issue, label change and close is more writes and a lag until someone runs the agent again. An issue closed or deleted on GitHub stays on the board. A server that reads GitHub itself, on a timer, costs no agent writes and keeps up by itself.

## What exists today

- **Planner - Projects** (`modules/schedule`, 0.1.16). Work is stored under `plan:<id>` in the space; `id` matches `^[A-Za-z0-9_-]{1,64}$` (`SC_ID`, `schedule-lib.js`). Work has `title` (120 characters), `start` and `end` (days), `owners`, `tags` (ids from the space's `tags` setting), `notes` (2000 characters), `done`, `column`, `ref` and `by`. `scClean` and `scValue` keep only those fields, so a field the module does not know is dropped by the next write from a page. A plan holds at most 1000 entries (`maxPlan`, `schedule-lib-file.js`). The `datesRequired` setting is on by default: work needs a start and an end. Work with a day is mirrored to the Calendar (`refs.produces`, `dated`, `mirror: "out"`).
- **The board** ([plan-projects-kanban](plan-projects-kanban.md), steps 1 to 5b built). `board:main` (`{ id, name, field: "column", columns, rowsBy? }`), else the `boardColumns` setting; `priority` gives the columns `inbox`, `now`, `next`, `later`, `done` (only `done` counts as done). `scSetColumn` sets `column` and `done` together; a `board:` write needs the `columns` permission (a `guards.keys` rule). `setColumn` is an action run on the server for agents.
- **The `tags` setting** is a `list` of at most 20 rows `{ id, label, icon, color }` (api-modules, settings), edited at space scope by an owner or the space's moderators.
- **The file format** (`modules/schedule/src/FORMAT.md`, `project-plan` version 1): entries with `id`, `kind`, `title`, `start`, `end`, `done`, `column`, `notes`, `tags`, and an optional `boards` list. Import **Replace the plan** keeps the file's ids and offers Undo.
- **What a server-run module action can do** (`server/module-actions.js`). A bundled module's library runs in a child process with Node's socket calls taken away (`server/module-actions-lockdown.js`) and, where the kernel allows, a network namespace of its own; "The run itself has no network". At most 10 writes per run, 64 KB of input, one second of the handler's time, only in the module's own data in that space. A module's page has a content security policy of `default-src 'none'` ([plan-weather-part](plan-weather-part.md), C1). So **no module code can reach GitHub**: not the page, not the server-run action. The fetch has to be core.
- **The weather engine** ([plan-weather-part](plan-weather-part.md), [architecture-weather](../architecture/architecture-weather.md)) is the pattern: core code with provider adapters (`server/weather-providers/`, the contract in `index.js`, a test stand-in loaded only under `WEATHER_TEST_STANDIN`), a host-level record of terms a person in authority accepts (`server/service-terms.js`, `DATA_DIR/service-terms.json`, `{ services: { <id>: { terms, by, at } } }`), the options on a bundled service-only module, and a check against the stand-in.
- **A server write that is not a person's request.** `fillStarter` (`server/index.js`, about line 14662) writes a template's starter content through `putModuleValue`, the same checked path as a page, with an owner's module rights (`templateRights`) though `by` the creator. That is the precedent for a system writer.
- **GitHub in this repository.** `.github/workflows/project-priority.yml` moves the issue on the project board when a `priority:` label is added; `.github/workflows/project-priority-sync.yml` makes the labels follow the board (Now, Next, Later set one label; Inbox or no column clears it; Done is left alone), and runs **only when started** (`workflow_dispatch`), so between runs a drag on GitHub's board is not in the labels. Both use a classic token with the `project` scope, because, as `documentation/TODO.md` ("Board setup") records, fine-grained tokens cannot reach a project owned by a user. `tools/roadmap-board-sync.mjs` is a Node GraphQL client for the board.
- **The repository** (read through GitHub's REST API on 2026-11-26): about 179 open and 203 closed issues, 786 pull requests, no milestones, and 15 labels: `priority: now`, `priority: next`, `priority: later`, `Planner`, and GitHub's defaults (`bug`, `enhancement`, `documentation`, `accessibility`, `critical`, `duplicate`, `good first issue`, `help wanted`, `invalid`, `question`, `wontfix`). Every issue title starts with an area and a colon.

## GitHub's terms and limits, as read

Read on 2026-11-26 at docs.github.com, by the planner (Thomas's rule: a service's terms are read before its adapter is written).

- **GitHub Terms of Service** (effective 2026-04-27), section H, API Terms: using the API means agreeing to the Terms plus section H. Abuse or excessively frequent requests may suspend API access, with a reasonable attempt to warn first. API tokens may not be shared to get past the rate limits. The API may not be used to download data for spam or to sell users' personal information. Use is subject to the GitHub Privacy Statement. GitHub "may offer subscription-based access" for high throughput or resale; neither applies here. Nothing in the Terms forbids commercial use of a free account or of the API within its limits, and the API costs nothing. A person must make the account (machine accounts are allowed, owned by a person who is responsible for them). **It passes Thomas's rule** (no paid service, no free tier that forbids commercial use).
- **Acceptable Use Policies**, section 7 and 8: information collected through the API must not be used for spam or sold; anyone collecting **personal information** must follow the Privacy Statement, use it only for the purpose the user authorized, secure it and answer removal requests. This is why the lean below pulls no logins.
- **Rate limits for the REST API**: 60 requests an hour without a token (per address); 5,000 an hour with a personal token. Secondary limits: at most 100 requests at once, 900 points a minute per endpoint, and a 403 or 429 when exceeded, with `retry-after` or `x-ratelimit-reset` to obey. **Best practices**: prefer webhooks to polling; if polling, poll on a fixed schedule and honour `x-poll-interval`; make requests one at a time; use conditional requests (`etag` sent back as `if-none-match`), and a `304 Not Modified` on an authorized request does not count against the limit; every request needs a `User-Agent` naming the application.
- **List repository issues** (`GET /repos/{owner}/{repo}/issues`): returns pull requests too (marked by a `pull_request` key, to be skipped); `state=all`, `since` (changed after a time), `per_page` up to 100. A fine-grained token needs only **Issues: read** (Metadata: read is always included). It works without a token for a public repository.
- **GraphQL limits**: 5,000 points an hour per user. Only needed if the board itself is read (below).

## The shape, with the leans

Each lean is a suggestion. Those marked "taken" are small and written down under the standing rule; those in "For Thomas" are his.

1. **One-way, GitHub to the space** (lean, For Thomas 1). GitHub is the source of truth; a pulled piece of work is read-only in the space (the page offers no edit, move or delete on it, and says "This comes from GitHub. Change it there." with the link), and the next pull overwrites anything changed some other way. Two-way (a drag in Chameleon changing the label on GitHub) needs a token that writes, conflict rules and a person accepting that Chameleon acts on GitHub; lean: not now, perhaps never, since the project manager and GitHub's own board already write there.
2. **Where it lives: a core part, `issues`** (lean, For Thomas 2). Module code cannot reach the network (above), so the fetch is core, shaped like weather: `server/issues.js` (the puller, its record and timer), `server/issue-providers/index.js` (the adapter contract), `github.js` (the first adapter) and `test-standin.js` (loaded only under `ISSUES_TEST_STANDIN`). Shaped as a part for [plan-core-parts](plan-core-parts.md) (`mountPart` is not built yet, so it moves in later, as weather will). The adapter turns a provider's answer into neutral records `{ number, title, open, labels: [{ name, color }], url, milestone?, created, closed? }`; nothing else in the core knows it is GitHub.
   - *Who maps the records into the plan.* (a) The part writes `plan:` entries in Planner - Projects' shape, naming the `schedule` module in the core, as weather names `weather`. (b) Planner - Projects maps them: a pure `scFromIssues(records, board, tags)` in its library, run by the server's action runner (no network needed: the records are handed in), with a system run's own larger write limit. (b) keeps the core from naming a module but needs a new kind of run (not an agent's) in `server/module-actions.js`. Lean: (a) for the first build, because it is smaller and the mapping is a dozen lines; For Thomas 3.
3. **What is pulled and how it maps** (taken, except where noted). Only issues, never pull requests. One work per issue, stored under `plan:gh-<number>`, so the key is the external id: a pull updates in place and never makes a second copy. Work gains one field, `source`: `{ from: "github", repo, number, url }`, kept by `scClean` and `scValue` (else a page's write would drop it) and in `FORMAT.md` and the schema.
   - `title`: GitHub's title as it is (area and colon included), cut to 120 characters with an ellipsis. The page draws `#<number>` beside it from `source`.
   - `column` and `done`: closed is `done`; open with `priority: now`, `next` or `later` is that column; any other open issue is `inbox`. Through `scSetColumn`, so `done` always equals the column's flag.
   - `tags`: each label other than `priority:` is a tag, id from its name (`good-first-issue`), label as on GitHub, its GitHub colour, the icon `tag`. The puller adds a missing row to the space's `tags` setting; the setting holds 20 rows and the repository has 12 such labels, and a label past the 20th is named in `notes` instead.
   - `notes`: one line with the link and, when set, the milestone's name (the repository has none today). Never the issue's body or comments: only what the board needs leaves GitHub's answer for the space.
   - `owners`: none. Logins are personal information under GitHub's policy, and matching a login to a member needs a stored link between accounts that does not exist. Assignees and authors are not pulled.
   - `start` and `end`: `start` the day it was made (UTC), `end` the day it closed, or the start day while it is open (`scClean` makes a one-day span). That meets `datesRequired` and orders each column oldest first. Lean: the pulled space has no Calendar module, or 382 dated copies flood it; a later choice could turn `datesRequired` off and write no days.
   - Milestones: a GitHub milestone becomes a Projects milestone `plan:ghm-<number>` with its work under it (`parent`), start its due day else its first day. None exist today, so this is in the contract and untested on real data.
   - Gone: an issue that is no longer in the full list (deleted or moved to another repository) has its work removed on the next full pull.
4. **The board's columns** (taken). Turning the pull on for a space sets its `boardColumns` to `priority` and writes `board:main` with exactly those five columns if it holds anything else; while the pull is on, a person's change of the columns is refused ("This board follows GitHub."). Rows and filters still work, since they are each person's view or `rowsBy`.
   - *The system writer.* The puller writes through `putModuleValue` as `fillStarter` does, with an owner's module rights (`templateRights`), so the module's guards, the key rule and the size caps still hold. Its `by` is a fixed system key, `system:issues`, which the page shows as "GitHub". New in the core: one recognised system key and the rule that only the puller may write as it.
5. **When it pulls** (taken). A **Pull now** button and a timer: every 10 minutes, `GET .../issues?state=all&since=<last>&per_page=100`, one request at a time, with the last `etag` sent as `if-none-match` (a 304 costs nothing with a token); once a day a full pull of every page (about 12 pages of 100, pull requests included) to find what is gone. A 403 or 429 waits for `retry-after` or `x-ratelimit-reset`; `x-poll-interval` is obeyed if longer. The first pull of 382 issues is about 12 requests and 382 local writes. Webhooks: skipped, they need a public address GitHub can reach.
6. **Credentials and terms.**
   - *The column from labels* (lean, For Thomas 4): the `priority:` labels give the column, so a fine-grained token with only **Issues: read** on this one repository is enough, or no token at all, since the repository is public (60 requests an hour, plenty at one every 10 minutes). The price: a drag on GitHub's board reaches the labels only when `project-priority-sync.yml` runs, and it runs only when started. Making that workflow also run on a schedule (say hourly) closes most of the gap with no change to Chameleon. *The column from the board itself* needs GraphQL and, per this repository's own note, a classic token (fine-grained tokens cannot reach a user's project), with the `read:project` scope (read-only); it also gives the board's own order inside a column, which labels cannot. Lean: labels first; the board as a second adapter only if the lag matters.
   - *The token* lives in an environment variable, `ISSUES_GITHUB_TOKEN`, read by the server only, sent only in the `Authorization` header to `https://api.github.com`, never logged, never in an answer, a page or a space's data. Without it the puller asks without a token. Redirects are followed only to `api.github.com`.
   - *The terms* are accepted once for the host by the person running it, as weather's are: the signed-in `admin` on a single install, the host's administrator on the host console. Lean (taken): one shared record for every outside service, `DATA_DIR/service-terms.json` (the weather file renamed, product unreleased), with `github` beside `met-norway`, and the **Weather terms** section becoming **Service terms**. No pull runs until GitHub's terms are accepted.
7. **Who configures it** (taken). The administrator accepts the terms and sets the token. The environment's owner turns the pull on for one space and names the repository (`owner/name`), in a **Follows GitHub** section of that space's Planner - Projects settings, as a `text` setting `githubRepo` at space scope; space-scope settings are an owner's or the space's moderators' (api-modules), and lean: owner only for this one, since it rewrites the whole plan. One repository per space; a repository may feed more than one space.
8. **What a person sees** (taken). In the plan's status bar: "From GitHub, pulled 3 minutes ago" and **Pull now** for someone with `edit`; after a failure, "GitHub did not answer; trying again at 14:20." (or "GitHub's terms are not accepted on this server.", "No such repository, or it is private."). Each pulled piece of work shows `#<number>` and a GitHub mark, and its menu has **Open on GitHub** (a new tab) instead of Edit, Move and Delete. Closed issues are all kept, in Done, which the board already folds on a phone; a window ("closed in the last 90 days") is a later setting only if the plan nears its 1000 entries (382 today).
9. **Agents and existing entries** (taken). An agent reads a pulled plan as any plan (useful to the project manager). `setColumn`, `updateEntry`, `setDone` and `deleteEntry` refuse a pulled entry with "This comes from GitHub. Change it there." An agent cannot turn a pull on or off. **A pulled space owns its plan**: the pull can be turned on only for a space whose plan is empty ("Clear the plan first, or use a new space."), and while it is on, nobody adds work by hand (the "+" and the add actions say the same sentence). For Bug Squash: lean, export its hand-written entries if they are wanted, then Clear, or make a fresh space. Turning the pull off leaves the work as ordinary entries, editable again, with `source` kept as a plain link.

## The contract

### Server (server-development)

- **The adapter** (`server/issue-providers/index.js`): `{ id, name, terms, needsToken: false, list({ repo, since, etag, token }) -> { status, etag, records, more } }`, plus `pollMs` and `fullEveryMs`. `github.js` asks only `api.github.com`, sends `User-Agent` from `userAgent` (`server/product-name.js`), `Accept: application/vnd.github+json` and the token when set, skips `pull_request`, and cuts each answer to 2 MB and 6 seconds. The stand-in answers from a fixture and counts requests.
- **The record** per environment, `issues.json` in the environment's data: `{ spaces: { <spaceId>: { provider, repo, on, last, etag, fullAt, error } } }`. Never the token.
- **Routes** (environment owner unless said): `GET /api/spaces/:id/issues-pull` (status: on, repo, last, next, error; anyone who may read the plan), `PUT /api/spaces/:id/issues-pull` (`{ repo, on }`; 409 "Clear the plan first, or use a new space." if the plan holds unpulled entries; 400 for a repo that is not `owner/name`; 403 for anyone else), `POST /api/spaces/:id/issues-pull/now` (someone with Projects' `edit`; 429 if a pull ran in the last minute). The terms: the weather terms routes, generalised to the shared record.
- **The write**: per pulled issue one `putModuleValue` of `plan:gh-<n>` (skipped when the value would not change), the `tags` setting when a label is new, `board:main` and `boardColumns` when the pull is turned on; deletes for what is gone. All as `system:issues` with `templateRights`; a person's write to a `plan:gh-*` key or to `board:` while the pull is on answers 403 "This comes from GitHub. Change it there."
- **What leaves the server**: GET requests to `api.github.com` naming the repository, the `since` time and the `etag`, with the token. Nothing of the space, the environment or its people.

### Pages (experience-design)

- Planner - Projects (module lane, patch bump): `source` in `scClean`, `scValue`, `FORMAT.md` and the schema; the `githubRepo` setting and the **Follows GitHub** section; the status line and **Pull now** (through a small `host.issues` SDK call routed through `public/module-host.js`, since a frame cannot reach the route itself); `#<number>`, the mark and **Open on GitHub** on the board, the List and the Timeline; read-only pulled entries; the action refusals.
- The shared **Service terms** section (`public/service-terms.js`) listing GitHub with its terms link.
